### AWS Lambda now supports customer-managed runtimes, giving platform teams centralized control over runtime contents and updates

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-customer-managed-runtimes/](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-customer-managed-runtimes/)
- **Published**: 2026-11-19 00:00:00
- **Fetched**: 2026-11-19 10:40:05

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>AWS Lambda now supports customer-managed runtimes for Lambda Event Functions (formerly Lambda functions). Customer-managed runtimes are a standalone resource type that fully decouples runtime management from function deployment. Platform teams gain centralized control over the runtime contents,&nbsp;updates, access, and lifecycle, including the ability to push updates to shared components without per-function redeployments. Application teams consume the runtime from their functions in the same way as a Lambda-managed runtime, preserving their familiar developer experience.</p> 
<p>Many organizations require every function to include approved components, such as SDKs, certificates, and security or monitoring tools. Previously, sharing these through Lambda Layers or container images meant redeploying every function to pick up a change. With customer-managed runtimes, platform teams manage these components in a central runtime, packaged as OCI container images in Amazon ECR and compatible with existing Docker and CI/CD tooling. Functions pick up updates automatically as Lambda recycles execution environments, so there's no need to redeploy each function or coordinate rollouts. Updates can be scheduled and staged to match change control policies, with centralized health metrics and rapid rollback. With this launch, the existing custom runtimes feature is renamed "bring your own language."</p> 
<p>AWS Lambda customer-managed runtimes is now generally available in all commercial AWS Regions. There is no additional charge for customer-managed runtimes; functions are billed at standard Lambda rates and standard Amazon ECR pricing applies to runtime images.</p> 
<p>To get started, build your runtime as a container image in Amazon ECR, starting from a Lambda base image or from scratch, then create a runtime, a version, and an alias. Application teams reference the runtime alias in their function configuration and keep deploying their code as .zip files. Share runtimes with other accounts or an AWS Organization by using a resource-based policy. You can create and manage customer-managed runtimes using the AWS CLI, AWS SDKs, CloudFormation, or AWS CDK. To learn more, see the <a href="https://docs.aws.amazon.com/lambda/latest/dg/runtimes-customer-managed.html" rel="noopener noreferrer" target="_blank">customer-managed runtimes documentation</a> and <a href="https://aws.amazon.com/blogs/compute/control-your-aws-lambda-runtimes-with-customer-managed-runtimes/" rel="noopener noreferrer" target="_blank">launch blog post</a>.</p>
</details>

### Amazon RDS now supports fast storage volume initialization

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-rds-fast-storage-volume-initialization/](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-rds-fast-storage-volume-initialization/)
- **Published**: 2026-11-19 01:00:00
- **Fetched**: 2026-11-19 04:54:38

<div class="entry-summary">
<p>Amazon RDS now initializes storage volumes faster when you perform a point-in-time restore (PITR), create a read replica, or convert a Single-AZ instance to Multi-AZ. Each of these operations creates storage volumes from a snapshot, and the data blocks are downloaded from Amazon S3 before you can access them. With fast storage volume initialization, you get a fully performant DB instance in a predictable amount of time.</p> 
<p>Previously, the initialization rate varied with your workload and with which blocks were accessed. As there was no dedicated bandwidth, so you could see increased I/O latency and had no way to tell when an instance would reach full performance. Now, each database instance is initialized at up to 4 TiB per hour, across every gp3 and io2 storage volume attached to the instance. If concurrent initialization across your account exceeds the available bandwidth, the remaining blocks initialize on a best-effort basis, so initialization is never slower than today. Your DB instance stays available and usable while initialization runs.</p> 
<p>Fast storage volume initialization is enabled by default and no action is required. To follow progress, use the StorageOperationStatus and StorageOperationPercentProgress fields in the Amazon RDS console, the DescribeDBInstances API, the AWS Command Line Interface (CLI), or AWS SDKs.</p> 
<p>This capability is available at no additional cost for RDS for MariaDB, RDS for MySQL, RDS for PostgreSQL, RDS for Db2, RDS for Microsoft SQL Server, and RDS for Oracle, in all commercial AWS Regions and the AWS GovCloud (US) Regions. To learn more, see <a href="https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_Storage.html" target="_blank">Amazon RDS storage</a> in the Amazon RDS User Guide.</p>
</div>

### Amazon CloudFront Functions now supports network calls

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/cloudfront-functions-network-calls/](https://aws.amazon.com/about-aws/whats-new/2026/11/cloudfront-functions-network-calls/)
- **Published**: 2026-11-19 01:00:00
- **Fetched**: 2026-11-19 10:40:05

<div class="entry-summary">
<p>Amazon CloudFront Functions can now make network calls and act on the response during a request. CloudFront Functions runs lightweight JavaScript at CloudFront edge locations to customize requests and responses. Previously, if your logic depended on data from another service, you had to use Lambda@Edge or move that logic to your origin. Now your functions can use real-time data to personalize, authenticate, or route requests at the edge, close to your viewers.</p> 
<p>With the new <i>cf.fetch()</i> method, your functions can call your API endpoints and use the response to decide how to handle each request. For example, you can check an AI agent's permissions and usage budget so that only authorized requests reach your API or MCP server, or send request signals to a security or fraud detection service to block or challenge bad traffic. With <i>cf.beacon()</i>, you can send analytics events in the background without slowing down viewers, even for content served from cache. Both methods take advantage of the origin settings already on your distribution, including origin access control (OAC), VPC origins, and connection reuse.</p> 
<p>Network calls are available at all CloudFront edge locations. They cost $0.10 per million calls, on top of CloudFront Functions invocation charges, and are included at no additional cost in the Pro plan and above in CloudFront flat-rate plans. <div class="entry-summary">
<p><a href="https://aws.amazon.com/cognito/">Amazon Cognito</a> now supports point-in-time recovery (PITR), so you can restore the user data in a user pool to an earlier time. Amazon Cognito helps you implement secure sign-in and access control for users, AI agents, and microservices. Previously, you had to build and maintain your own export and restore process, and restored users received new identifiers and had to reset their passwords.</p> 
<p>With PITR, you choose a recovery point, preview how many users, groups, multi-factor authentication (MFA) settings, and passkeys the recovery will create, update, or delete, and then start or cancel the recovery. Recovered users keep their identifiers, passwords, MFA settings, and passkeys, so they can sign in without resetting their credentials. For example, if a script deletes or modifies users by mistake, you can restore the user data to the moment before it ran.</p> 
<p>PITR is enabled automatically for user pools on the Essentials and Plus feature plans at no additional charge. The recovery window is up to 1 day on Essentials and up to 14 days on Plus. You can initiate and manage a recovery using the AWS Management Console, the Amazon Cognito API, AWS Command Line Interface (AWS CLI), or AWS SDKs. PITR is available in all <a href="https://aws.amazon.com/about-aws/global-infrastructure/regional-product-services/">AWS Regions</a> where Amazon Cognito is available. <div class="entry-summary">
<p>Amazon VPC Flow Logs now adds Amazon Elastic Kubernetes Service (Amazon EKS) metadata to flow log records. Each record identifies the pod that sent or received the traffic, along with its cluster, namespace and labels. This makes it faster to investigate security events, understand traffic patterns, and troubleshoot network issues in your EKS clusters, without running monitoring software on your nodes.</p>
<p>Amazon EKS runs pods on Amazon EC2 instances, called nodes, and many pods can share one node's network interfaces. Previously, flow log records showed the network interface and IP address for each flow, not the pod behind it. Pods are short-lived, so by the time you investigated unexpected traffic, that IP address could belong to a different pod. To trace traffic back to the right pod, teams built custom tools or ran monitoring software on every node. Now, each record names the pod that sent or received the traffic, so one log gives you both VPC and Kubernetes context. For example, if a pod sends unexpected traffic to a database in your VPC, the record shows the pod and its namespace, even after that pod is replaced.</p>
<p>To get started, create a flow log for your cluster's VPC or subnets, and add the EKS fields to the log format. You don't need to change your cluster or applications. The fields are available for pods on Amazon EC2 instances, including EKS Auto Mode, managed node groups and self-managed nodes, that use the Amazon VPC CNI plugin for Kubernetes. Logs go to the same destinations as before, so your existing analytics tools keep working. EKS metadata is available at no additional charge. Standard VPC Flow Logs charges for log delivery and storage still apply. This feature is supported in all AWS Regions where Amazon EKS is available.
