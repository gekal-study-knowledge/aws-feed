### Amazon SNS now supports push notifications in four additional AWS Regions

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-sns-push-four-regions/](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-sns-push-four-regions/)
- **Published**: 2026-11-13 01:00:00
- **Fetched**: 2026-11-13 08:09:10

<div class="entry-summary">
<p><a href="https://aws.amazon.com/sns/">Amazon Simple Notification Service (Amazon SNS)</a> now supports sending push notifications in the Asia Pacific (Hyderabad), Asia Pacific (Melbourne), Europe (Zurich), and AWS GovCloud (US-East) Regions.</p>

<p>For the full list of Regions from which you can send push notifications, see <a href="https://docs.aws.amazon.com/sns/latest/dg/sns-mobile-push-supported-regions.html">Supported Regions and Countries</a> in the Amazon SNS Developer Guide. ### Amazon Connect Customer supports merging and linking related cases in the agent workspace

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-connect-cases-merge-link/](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-connect-cases-merge-link/)
- **Published**: 2026-11-13 02:00:00
- **Fetched**: 2026-11-13 08:09:10

<div class="entry-summary">
<p>Amazon Connect Customer now lets agents merge and link related cases in the agent workspace, so they can resolve customer issues faster and respond consistently. When a customer contacts a business about the same issue more than once, or on different channels, the history can end up split across several cases. Agents can merge those cases into one case with a single, consolidated history. For example, an agent can merge the chat and email cases a customer opened about a delayed shipment.</p> 
<p>Agents can also link related cases, such as cases from different customers affected by the same issue, so they can coordinate one consistent response for every affected customer.</p> 
<p>Cases is available in the following AWS regions: US East (N. Virginia), US West (Oregon), Canada (Central), Europe (Frankfurt), Europe (London), Asia Pacific (Seoul), Asia Pacific (Singapore), Asia Pacific (Sydney), Asia Pacific (Tokyo), and Africa (Cape Town). To learn more and get started, visit the Cases <a href="https://aws.amazon.com/products/connect/customer/cases/" target="_blank">webpage</a> and <a href="https://docs.aws.amazon.com/connect/latest/adminguide/cases.html" target="_blank">documentation</a>.</p>

### Amazon MWAA now supports fine-grained access control with IAM Identity Center and multi-team environments

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/mwaa-fine-grained-access-control/](https://aws.amazon.com/about-aws/whats-new/2026/11/mwaa-fine-grained-access-control/)
- **Published**: 2026-11-13 03:00:00
- **Fetched**: 2026-11-13 08:09:10

<div class="entry-summary">
<p>Amazon Managed Workflows for Apache Airflow (Amazon MWAA) now supports fine-grained access control, giving administrators precise control over who can access which workflows and resources in an Apache Airflow environment. Fine-grained access control is delivered through two new capabilities: IAM Identity Center integration and multi-team environments.</p>
<p>With IAM Identity Center integration, users sign in to the Apache Airflow UI with their corporate identity provider. Authorization is evaluated per request using IAM policies attached to IAM Identity Center Permission Sets, with condition keys that scope access by resource type (DAGs, connections, variables, pools, and more), action, and specific resource ID.</p>
<p>With multi-team environments, several teams can share a single MWAA environment. Each team gets its own DAG folder in Amazon S3, and users see only shared DAGs plus their own teams' DAGs based on IAM Identity Center group membership. Teams reduce cost through shared infrastructure and simplify management by configuring environment settings once. Multi-team environments are based on the Apache Airflow multi-team feature, which is currently in preview.</p>
<p>These features are available in all <a href="https://docs.aws.amazon.com/mwaa/latest/userguide/get-started.html#regions" target="_blank">AWS Regions</a> where Amazon MWAA is available.</p>
<p>To learn more, visit the <a href="https://docs.aws.amazon.com/mwaa/latest/userguide/identity-center-integration.html" target="_blank">IAM Identity Center integration documentation</a> and the <a href="https://docs.aws.amazon.com/mwaa/latest/userguide/multi-team-environments.html" target="_blank">multi-team environments documentation</a>.</p>
</div>

### Amazon Cognito now supports OAuth 2.0 token exchange

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/cognito-token-exchange/](https://aws.amazon.com/about-aws/whats-new/2026/11/cognito-token-exchange/)
- **Published**: 2026-11-13 07:00:00
- **Fetched**: 2026-11-13 13:52:30

<div class="entry-summary">
<p><a href="https://aws.amazon.com/cognito/">Amazon Cognito</a> now supports OAuth 2.0 token exchange (RFC 8693). Amazon Cognito helps you add sign-up, sign-in, and access control to your web applications, mobile applications, and AI agents. With token exchange, a service or AI agent acting on a user's behalf can exchange the user's token for a new token scoped to a specific downstream service. Previously, a service that called another service on a user's behalf had to forward the user's original token or build and maintain its own token minting logic.</p> 
<p>With token exchange, you can issue a new token that has a narrower scope than the original token, is bound to a single audience, and comes without a refresh token. When you include an actor token, Cognito adds an act claim that identifies the intermediary, so downstream services can tell a request that an agent made on a user's behalf from one the user made directly. For example, a Model Context Protocol (MCP) server can exchange a user's token for a narrowly scoped token to call a backend API, with the act&nbsp;claim recording the MCP server as the actor.</p> 
<p>You can exchange tokens through the token endpoint or with the new <a href="https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_GetDerivedToken.html">GetDerivedToken API</a>. Token exchange is available on the Essentials and Plus feature plans in all <a href="https://aws.amazon.com/about-aws/global-infrastructure/regional-product-services/">AWS Regions</a> where Amazon Cognito is available. To learn more, see <a href="https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-token-exchange.html">exchanging tokens for downstream services</a> in the Amazon Cognito Developer Guide.</p>
</div>

### Amazon RDS for Oracle reduces downtime for automatic minor version upgrades and scheduled maintenance

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/rds-oracle-reduces-maintenance-downtime-for-amvu-scheduled-upgrades/](https://aws.amazon.com/about-aws/whats-new/2026/11/rds-oracle-reduces-maintenance-downtime-for-amvu-scheduled-upgrades/)
- **Published**: 2026-11-13 17:00:00
- **Fetched**: 2026-11-14 05:16:46

<details class="entry-summary">
<summary>詳細を表示</summary>
<p><a href="https://aws.amazon.com/rds/oracle/">Amazon Relational Database Service (Amazon RDS) for Oracle</a> now reduces downtime for automatic minor version upgrades, as well as minor version upgrades and operating system updates scheduled for your maintenance window. Shorter maintenance makes it easier to stay current on the latest Oracle minor versions and operating system updates with less disruption to your applications. If you turned on automatic minor version upgrade, your DB instances benefit automatically.</p> 
<p>To apply these upgrades and updates, RDS has to set up new resources as part of the maintenance. Previously, RDS set up these resources after the maintenance started, which made your downtime longer. Now, RDS prepares them up to 30 minutes before your maintenance window, while your DB instance keeps serving your workload. When the maintenance window opens, your DB instance is offline for less time because resources required for the maintenance are already prepared. This applies to both Enterprise Edition and Standard Edition 2 DB instances.</p> 
<p>The preparation never blocks or delays your own operations, and your DB instance stays available while RDS prepares. If a change that you make conflicts with the preparation, RDS rolls back the staged resources, and your change goes ahead. If the preparation can't finish, RDS still applies the maintenance in your window, without the preparation. New RDS events tell you when the preparation starts, when it finishes, and when it can't finish.&nbsp;RDS for Oracle will continue to introduce improvements that further reduce maintenance downtime.</p> 
<p>This capability is available at no additional cost in all commercial AWS Regions and the AWS GovCloud (US) Regions where Amazon RDS for Oracle is available. To learn more, see <a href="https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/maintenance-preparation.html" rel="noopener noreferrer" target="_blank">Maintenance preparation</a>, <a href="https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_Events.Messages.html" rel="noopener noreferrer" target="_blank">Amazon RDS event categories and event messages</a>, and <a href="https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_UpgradeDBInstance.Maintenance.html" rel="noopener noreferrer" target="_blank">Maintaining a DB instance</a> in the Amazon RDS User Guide.</p>
</details>

### AWS Secrets Manager now supports cross-account replication

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/secrets-manager-cross-account/](https://aws.amazon.com/about-aws/whats-new/2026/11/secrets-manager-cross-account/)
- **Published**: 2026-11-13 17:00:00
- **Fetched**: 2026-11-14 05:16:46

<div class="entry-summary">
<p>AWS Secrets Manager now supports cross-account replication, enabling you to maintain a synchronized copy of a primary secret in a secondary AWS account for cross-account access, backup, and disaster recovery. Cross-account replication extends the existing multi-Region replication capability across account boundaries.</p> 
<p>With cross-account replication, platform or security teams can own and rotate a secret centrally, and each consuming account gets a local, always-current copy without any shared KMS keys or cross-account secret policies. The replica secret is a full, independent resource, encrypted with a customer managed KMS key owned by the replica account. Secrets Manager updates it automatically whenever the primary secret's value changes, including rotations.</p> 
<p>You can keep a live copy of critical secrets in a dedicated recovery or failover account, isolated from ransomware or a compromised primary account. If needed, the replica can be promoted to a standalone secret.</p> 
<p>Cross-account replication is available in all AWS Regions where Secrets Manager is available. For a list of regions where Secrets Manager is available, see the <a href="https://aws.amazon.com/about-aws/global-infrastructure/regional-product-services/" rel="noopener noreferrer" target="_blank">AWS Region table</a>.</p> 
<p>To learn more, see <a href="https://docs.aws.amazon.com/secretsmanager/latest/userguide/cross-account-replicate-secrets.html" rel="noopener noreferrer" target="_blank">Replicate secrets across AWS accounts in the Secrets Manager User Guide</a> and the <a href="https://docs.aws.amazon.com/secretsmanager/latest/apireference/API_AssociateCrossAccountReplica.html" rel="noopener noreferrer" target="_blank">AssociateCrossAccountReplica API reference</a>. <p><b>Bulletin ID:</b> 2026-181-AWS<br /> <b>Publication Date:</b> 11/12/2026 13:00 PM PST</p> 
<p><b>Description:</b></p> 
<p>We identified CVE-2026-127119, an issue in the EMR module of AWS SDK for pandas (awswrangler) from version 1.1.0 before 3.18.0. When a cluster is created without an explicit log location, the library uses a predictable default S3 bucket name for the cluster logs without verifying that the caller's account owns that bucket. <p><b>Impacted versions:</b> &gt;= 1.1.0 AND &lt; 3.18.0</p>
