### AWS Global Accelerator now preserves client IPs for NLBs with TLS listeners

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/global-accelerator-client-ip-nlb-tls/](https://aws.amazon.com/about-aws/whats-new/2026/11/global-accelerator-client-ip-nlb-tls/)
- **Published**: 2026-11-24 01:00:00
- **Fetched**: 2026-11-24 08:19:09

<div class="entry-summary">
<p>AWS Global Accelerator now preserves the client IP address for traffic sent to Network Load Balancer (NLB) endpoints with TLS listeners. You can terminate TLS at your NLB and still see the original client IP address in your application. This means you can apply security groups, geo-blocking, rate limiting, fraud detection, audit logging, allowlists, and compliance controls based on the real client IP.</p> 
<p>Previously, you couldn't add an NLB with a TLS listener to an accelerator that had client IP address preservation enabled. You had to choose between terminating TLS at the NLB and seeing the real client IP address. With this launch, you get both. This helps with workloads that need TLS termination at Layer 4, such as non-HTTP TCP protocols, applications that require static or Elastic IP addresses, and high-throughput traffic where a Layer 7 load balancer isn't a fit.</p> 
<p>To enable this feature, add an NLB with a TLS listener as an endpoint to an accelerator with client IP address preservation setting turned on, the same way you add any NLB. No additional configuration is required! Client IP address preservation for NLBs with TLS listeners is available at no additional charge in all AWS commercial Regions, excluding the AWS GovCloud (US) and China Regions. Standard Global Accelerator pricing applies.</p> 
<p>To learn more, see <a href="https://docs.aws.amazon.com/global-accelerator/latest/dg/preserve-client-ip-address.html" rel="noopener noreferrer" target="_blank">Client IP address preservation</a> in the AWS Global Accelerator Developer Guide and <a href="https://docs.aws.amazon.com/elasticloadbalancing/latest/network/create-listener.html" rel="noopener noreferrer" target="_blank">Create a listener for your Network Load Balancer</a> in the User Guide for Network Load Balancers.</p>
</div>

### Amazon CloudFront Announces HTTP/2 Support for Connections to Origins

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/01/amazon-cloudfront-http2-origins/](https://aws.amazon.com/about-aws/whats-new/2026/01/amazon-cloudfront-http2-origins/)
- **Published**: 2026-11-24 02:00:00
- **Fetched**: 2026-11-24 08:19:09

<div class="entry-summary">
<p>Amazon CloudFront now supports HTTP/2 connections to custom origins and VPC origins. HTTP/2 lets CloudFront send many requests over fewer connections to your origin. This means fewer connections and TLS handshakes for your origin to handle, which improves performance for API and agentic workloads, such as AI agents calling MCP servers or mobile and web apps calling backend APIs.</p> 
<p>Until now, CloudFront connected to origins only over HTTP/1.1, which handles one request at a time per connection. When traffic spiked, for example when an AI agent made many tool calls at once, CloudFront had to open more origin connections. Each new connection added latency and load. With HTTP/2, those requests share connections, so your origin does less work and responds faster. HTTP/2 is also supported for WebSocket connections that support extended CONNECT. If your origin doesn't support HTTP/2, CloudFront automatically falls back to HTTP/1.1, so you don't need to change anything on your origin.</p> 
<p>HTTP/2 to origins is available from all CloudFront edge locations. There is no additional cost for using HTTP/2 to origins. To learn more, visit <a href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesOrigin.html#DownloadDistValuesOriginHttpVersion">Origin HTTP version</a> in the CloudFront Developer Guide.</p>
</div>

- **Published**: 2026-11-24 03:51:00
- **Fetched**: 2026-11-24 08:19:09

<div class="entry-summary">
<p>AWS WAF now offers simplified pricing that follows what you protect instead of how you configure it. Previously, you paid separate charges for each web ACL, rule, rule group subscription, and capacity tier, making every security decision a billing calculation. Now, your bill follows three dimensions: the resources you protect, the traffic AWS WAF inspects, and the level of protection you apply. This makes the cost-benefit trade-off easy to understand, and adding or changing rules no longer changes your rate.</p> 
<p>The new model makes protection costs predictable before you deploy. Each web ACL now includes up to 2,500 WCU at no extra charge, up from 1,500, and you can add rules such as Bot Control common protections or the Anti-DDoS rule group without additional fees. You pay a resource fee for each protected resource, a base request fee for every request AWS WAF inspects, and a premium request fee only for traffic evaluated by advanced protections like Bot Control targeted protections, Fraud Control, API Security, and AI Security.</p> 
<p>AWS WAF's new pricing is available today in all AWS commercial Regions, including Cape Town, Hong Kong, Hyderabad, Jakarta, Malaysia, Melbourne, Mumbai, New Zealand, Osaka, Seoul, Singapore, Sydney, Taipei, Thailand, Tokyo, Calgary, Frankfurt, Ireland, London, Milan, Paris, Spain, Stockholm, Zurich, Tel Aviv, Sao Paulo, N. ### CVE-2026-134056 - Out-of-bounds write in padded block cipher decryption in AWS-LC

- **Link**: [https://aws.amazon.com/security/security-bulletins/rss/2026-196-aws/](https://aws.amazon.com/security/security-bulletins/rss/2026-196-aws/)
- **Published**: 2026-11-24 05:29:41
- **Fetched**: 2026-11-24 08:19:10

<div class="entry-summary">
<p><b>Bulletin ID:</b> 2026-196-AWS<br /> <b>Publication Date:</b> 11/23/2026 12:00 PM PST</p> 
<p><b>Description:</b></p> 
<p> We identified CVE-2026-134056, an out-of-bounds write issue in AWS-LC's padded block cipher decryption. It affects applications that decrypt CBC or ECB ciphertext with PKCS7 padding over multiple update calls. If the output buffer is the minimum documented size, AWS-LC can write one byte past its end. This might crash the application or corrupt adjacent memory. This issue does not disclose data. The aws-lc-rs StreamingDecryptingKey API has a similar issue with cbc_pkcs7 and ecb_pkcs7. Its less_safe_update function can write up to one block (16 bytes for AES) past the buffer. Single-call decryption is not affected. Neither is decryption without padding, nor modes such as CTR, CFB, and GCM.</p> 
<p>Customers of AWS services do not need to take action.</p> 
<p><b><a href="https://aws.amazon.com/security/security-bulletins/2026-196-aws/">Refer to the article</a> for the most up-to-date and complete information.</b></p>
</div>

- **Published**: 2026-11-24 06:54:18
- **Fetched**: 2026-11-24 08:19:10

<div class="entry-summary">
<p><b>Bulletin ID:</b> 2026-197-AWS<br /> <b>Publication Date:</b> 11/23/2026 13:30 PM PST</p> 
<p><b>Description:</b></p> 
<p>Amazon SSM Agent is the AWS Systems Manager agent that runs on EC2 instances so they can be managed through Systems Manager.</p> 
<p>We identified CVE-2026-134069, an issue in Amazon SSM Agent on AWS-provided Windows Server AMIs released before 2026-09-09, where instances launched from the same AMI shared one instance registration key. On instances managed through Default Host Management Configuration, a local user without administrative privileges might be able to obtain the instance's Default Host Management Configuration role credentials.</p> 
<p><b>Impacted versions:</b></p> 
<p>Amazon SSM Agent &lt; 3.3.5226.0 on AWS Windows Server AMIs released before 2026-09-09. Instances launched from these AMIs remain affected after an in-place agent upgrade.</p>
