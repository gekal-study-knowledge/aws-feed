### Amazon EKS Auto Mode and Karpenter now support Dynamic Resource Allocation

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-eks-auto-mode-karpenter-dra/](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-eks-auto-mode-karpenter-dra/)
- **Published**: 2026-11-09 15:00:00
- **Fetched**: 2026-11-10 10:51:35

<div class="entry-summary">
<p>Amazon Elastic Kubernetes Service (Amazon EKS) now supports Dynamic Resource Allocation (DRA) for NVIDIA GPUs and Elastic Fabric Adapter (EFA) network devices when using Amazon EKS Auto Mode and Karpenter. You can now define the device attributes your Kubernetes workloads need with DRA, share GPU devices across Pods, and allocate topology-aligned GPU and EFA devices while Amazon EKS Auto Mode and Karpenter dynamically scale Amazon EC2 instances based on workload demand.</p> 
<p>With DRA, you define ResourceClaim or ResourceClaimTemplate objects that describe what GPU or EFA devices can be allocated to workloads, by model, architecture, or other attributes. When running distributed training or inference, you can define PCIe-aligned GPU and EFA devices for optimal performance. Workloads then request those DRA objects in their configuration, and Karpenter automatically launches the lowest-cost instances that match. When using Amazon EKS Auto Mode, the NVIDIA DRA driver and EFA DRA driver (DRANET) are built-in, and you simply define your DRA objects and use them in your workloads. Amazon EKS Auto Mode automatically prevents workloads using DRA and workloads using device plugins for the same device type from running on the same nodes to mitigate the risk of silent device oversubscription during migrations.</p> 
<p>DRA support for Amazon EKS Auto Mode and Karpenter is available in all AWS Regions, except the AWS GovCloud (US) Regions and the China Regions. DRA support is available for all Kubernetes versions in Karpenter, and for Kubernetes versions 1.36 and newer in <a href="https://aws.amazon.com/eks/auto-mode/">Amazon EKS Auto Mode</a>. To learn more, see the DRA documentation in the <a href="https://docs.aws.amazon.com/eks/latest/userguide/device-management.html">Amazon EKS User Guide</a> and <a href="https://karpenter.sh/docs/tasks/dra/">Karpenter documentation</a>.</p>
</div>

### AWS Analytics services now support Workday Data Cloud integration

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/aws-analytics-workday-data-cloud/](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-analytics-workday-data-cloud/)
- **Published**: 2026-11-09 17:00:00
- **Fetched**: 2026-11-10 10:51:35

<div class="entry-summary">
<p>Today, AWS announces a new bi-directional, zero-copy integration between AWS Analytics services and Workday Data Cloud. Instead of building and maintaining ETL pipelines to replicate data between systems, joint customers can now query across their AWS and Workday datasets in place, without moving or copying data, while retaining existing security controls in both environments.</p>
<p>From AWS, you can use Amazon SageMaker Unified Studio, Amazon EMR, AWS Glue, Amazon Redshift, and Amazon Athena to query Workday data through Workday Live Data Query or federate to Apache Iceberg tables in Workday Data Cloud through catalog federation. Configure a connection in SageMaker Unified Studio, AWS Glue, or AWS Lake Formation consoles and begin querying immediately. Access is governed by AWS and Workday permissions.</p>
<p>From Workday, you can register your AWS Glue Data Catalog Iceberg REST endpoint as an external catalog in Workday Analytics and query your AWS Iceberg tables directly. Common use cases include joining workforce data with business data for talent analytics, workforce planning, and machine learning.</p>
<p>This integration is available in all AWS commercial regions where AWS Glue is available. To learn more, see the <a href="https://docs.aws.amazon.com/glue/latest/dg/connecting-to-data-workday.html" target="_blank">AWS Glue User Guide</a>, the <a href="https://doc.workday.com/admin-guide/en-us/workday-data-cloud/data-out/workday-data-lake/workday-data-lake.html" target="_blank">Workday Data Cloud integration with AWS on Workday Data Cloud</a>, and the <a href="https://aws.amazon.com/blogs/big-data/introducing-the-workday-data-cloud-integration-with-aws/" target="_blank">AWS Big Data Blog post</a>.</p>

### Introducing AWS Nitro Sandboxes on Amazon EKS, ECS and EC2 for hardware isolated pods, tasks and VMs

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/nitro-sandboxes-eks-ecs-ec2/](https://aws.amazon.com/about-aws/whats-new/2026/11/nitro-sandboxes-eks-ecs-ec2/)
- **Published**: 2026-11-09 17:00:00
- **Fetched**: 2026-11-10 10:51:35

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>AWS Nitro Sandboxes are now available as lightweight VMs managed by the Nitro Hypervisor. You can use Nitro Sandboxes for an Amazon EKS pod, or Amazon ECS task, or lightweight Virtual Machines (VMs), including AI agents running inside them, in their own hardware-isolated virtual machine powered by the <a href="https://aws.amazon.com/ec2/nitro/">AWS Nitro System</a>. Each workload gets the isolation boundary of a Nitro isolated virtual machine. This allows you to safely run untrusted, multi-tenant, or regulated workloads within the resources of a single instance.</p> 
<p>Nitro Sandboxes run on your EC2 instances with near-native EC2 performance and inherits Nitro-hypervisor isolation. You can also validate your workloads through cryptographic attestation, so that secrets are released only to Nitro Sandboxes that have proven their integrity. With Nitro Sandboxes, you can safely execute LLM-generated code in an isolated environment of its own all while improving utilization and lowering compute costs by securely sharing a single EC2 instance across multiple agentic workloads. You can easily enable EKS pods or ECS tasks to run on Nitro Sandboxes and each pod or task gets its own isolated environment. Enabling Nitro Sandboxes in EKS or ECS is a one-line change and each pod or task gets its own VM, with your workloads remaining fully native (Pod Identity, VPC CNI, EBS/EFS/S3 storage, and CloudWatch all work out of the box). If you want full control, run Nitro Sandboxes directly on EC2 with your own AMI, orchestration, and with virtual machine monitors (VMMs). Amazon Linux and Firecracker are natively supported, and patches for other options are available today.</p> 
<p>AWS Nitro Sandboxes are available today on most nitro-based ec2 instances, in all commercial regions worldwide, at no additional charge.</p> 
<p>To learn more and get started, see the <a href="https://docs.aws.amazon.com/eks/latest/userguide/sandboxing.html">EKS User Guide</a> or <a href="https://docs.aws.amazon.com/AmazonECS/latest/developerguide/isolated-confidential-tasks.html">ECS User Guide</a>. For implementation details or to fully customize your Nitro Sandbox usage, see the <a href="https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-nitro-sandboxes.html">Nitro Sandboxes documentation</a> in the EC2 user guide.</p>
</details>

### Amazon Route 53 Profiles now supports multiple Profiles per VPC

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/route-53-profiles-multiple-per-vpc/](https://aws.amazon.com/about-aws/whats-new/2026/11/route-53-profiles-multiple-per-vpc/)
- **Published**: 2026-11-09 17:00:00
- **Fetched**: 2026-11-10 10:51:35

<div class="entry-summary">
<p><a href="https://aws.amazon.com/route53/">Amazon Route 53 Profiles</a> now lets you associate more than one Profile with a VPC. Previously, a VPC could have only one Profile, so teams that managed Route 53 configurations separately (for example, security teams managing DNS Firewall rule groups while cloud infrastructure and network admin teams manage private hosted zones and Resolver forwarding rules) all had to share a single Profile and associate their private hosted zones, Resolver rules, and DNS Firewall rule groups with it.</p> 
<p>With this launch, you can now associate multiple Profiles with the same VPC and set a priority for every Profile. Route 53 evaluates a VPC's Profiles in priority order, starting with the lowest number, so you can keep shared Route 53 configurations in one Profile and team-specific configurations in another without merging them, while assigning them the right priority. Combined with <a href="https://aws.amazon.com/about-aws/whats-new/2026/03/amazon-route-53-profiles-granular-iam/">the granular IAM permissions</a> launched in March 2026, multiple Profiles per VPC improves security posture by letting each team own and manage its own Profile with least-privilege permissions.</p> 
<p>This capability is available in all AWS Regions where Route 53 Profiles is available.</p> 
<p>Each Profile-VPC association is billed at standard Route 53 Profiles pricing. For details, see <a href="https://aws.amazon.com/route53/pricing/">Amazon Route 53 pricing</a>. To learn more, see <a href="https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/profiles.html" rel="noopener noreferrer" target="_blank">Route 53 Profiles</a> in the Amazon Route 53 Developer Guide.</p>
</div>
