### AWS announces AWS Interconnect - last mile preview with Equinix

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/interconnect-last-mile-preview-equinix/](https://aws.amazon.com/about-aws/whats-new/2026/11/interconnect-last-mile-preview-equinix/)
- **Published**: 2026-11-05 02:00:00
- **Fetched**: 2026-11-05 03:24:15

<div class="entry-summary">
<p>AWS Interconnect - last mile is now available in preview with Equinix. You can connect your infrastructure across Equinix's global network of 282 data centers worldwide to AWS in a few clicks.</p> 
<p>Interconnect - last mile gives you managed, private, and resilient connections to AWS, so you don't have to order cross-connects or configure routers. To set up in the AWS Management Console, choose an AWS Region, a bandwidth speed, a Direct Connect gateway, and your Equinix Fabric One project ID. AWS generates an activation key, which you enter in the Equinix Fabric One portal to complete the setup. You can also initiate the connection from the Equinix Fabric One portal. AWS and Equinix set up quad-redundant capacity in advance, across two locations and four separate links, with BGP peering, VLANs and ASNs configured for you. Every connection is built for maximum resilience and comes with a 99.99% availability SLA. Traffic between AWS and Equinix edge devices is encrypted with MACsec by default.</p> 
<p>During the preview, you can order 1 Gbps Interconnect - last mile connections at no charge to the US West (N. California) Region through the San Jose metro and to the US East (N. Virginia) Region through the Northern Virginia metro. When Interconnect - last mile with Equinix becomes generally available, you'll be able to scale bandwidth from 1 Gbps to 100 Gbps in the console. You can create connections using the console, the AWS CLI, or the API. Partners can integrate using the open API package on <a href="https://github.com/aws/Interconnect">GitHub</a>. To learn more, see the <a href="https://docs.aws.amazon.com/interconnect/">AWS Interconnect - last mile documentation</a>.</p>

### Amazon RDS for Oracle now supports copying option groups during cross-Region snapshot copy

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-rds-oracle-cross-region-snapshot-copy-option-group/](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-rds-oracle-cross-region-snapshot-copy-option-group/)
- **Published**: 2026-11-05 03:40:00
- **Fetched**: 2026-11-05 09:05:25

<div class="entry-summary">
<p>Amazon RDS for Oracle now lets you copy the option group associated with a DB snapshot when you copy that snapshot to another AWS Region.</p> 
<p>Amazon RDS for Oracle uses option groups to enable and configure features that make it simple to manage your databases. Option groups are specific to the AWS Region where you create them. Previously, customers wanting to replicate RDS backups that had option groups to a different AWS Region had to copy the snapshot without the option group and then recreate the option group in the target Region before restoring the snapshot. Now, you no longer need to separate the steps and can instead initiate the snapshot copy and specify the option group copy in the same request as the snapshot copy.</p> 
<p>The existing boolean parameter <b>CopyOptionGroup</b> on the <b>CopyDBSnapshot</b> API and CLI commands now also support cross-Region copy, along with cross-account copy. You can now copy options groups to the destination snapshot in the target AWS Region from the source snapshot by setting this parameter to <b>true</b>.</p> 
<p>This capability is available on Amazon RDS for Oracle in all commercial AWS Regions and the AWS GovCloud (US) Regions. To learn more, review the <a href="https://docs.aws.amazon.com/AmazonRDS/latest/APIReference/API_CopyDBSnapshot.html" target="_blank">Amazon RDS API Documentation</a>.&nbsp;</p>
</div>

### Amazon ECS Managed Daemons can now collect json-file logs from application containers on Amazon ECS Managed Instances

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-ecs-managed-instances-json-file-log-driver/](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-ecs-managed-instances-json-file-log-driver/)
- **Published**: 2026-11-05 06:29:00
- **Fetched**: 2026-11-05 09:05:25

<div class="entry-summary">
<p><a href="https://aws.amazon.com/ecs/">Amazon Elastic Container Service</a> (Amazon ECS) introduces json-file log driver support for Amazon ECS Managed Instances and log driver volumes for Amazon ECS Managed Daemons. Together, these features let you collect application logs with the observability agent of your choice and forward them to any destination you choose.<br /> <br /> With this launch, your application containers on ECS Managed Instances can write their logs as local files in standard Docker json-file format, which most observability agents read natively. Your managed daemons can directly read these files through a volume mount, without specifying host bind mount paths or requiring root privileges. As a result, one managed daemon on each instance can collect logs from every application container that uses the json-file log driver. Amazon ECS keeps each container's logs in a dedicated directory named with the container ID and retains them until the container is removed, so your managed daemon can use native file-based log collection and trace every log back to the container that produced it.<br /> <br /> To get started, set the log driver to json-file in the logConfiguration of your application task definition. Next, register a daemon task definition that specifies a volume with logDriverVolumeConfiguration, and mount the volume into your daemon container using mountPoints. You can configure this using the AWS Management Console, AWS CLI, API, AWS SDKs or AWS CloudFormation. This feature is available in all commercial AWS Regions where Amazon ECS Managed Instances and Managed Daemons are available, at no additional cost. To learn more, refer to our <a href="https://docs.aws.amazon.com/AmazonECS/latest/developerguide/managed-daemons-task-definitions.html#managed-daemons-volumes">documentation</a> page and visit <a href="https://aws.amazon.com/ecs/managed-instances/">Amazon ECS Managed Instances</a>.</p>
</div>

<p>AWS Systems Manager Parameter Store now supports 13 new parameter data types that automatically validate parameter values when you create or update a parameter. With built-in validation, you can stop malformed configuration values, such as an invalid IP address, AWS account ID, or JSON document, before your applications read them, without writing your own validation logic.&nbsp;These types allow you to better organize your parameters across your workloads. You can filter by type when calling the DescribeParameters API or when browsing parameters in the Parameter Store console.<br /> <br /> The following data types are available for both standard and advanced parameters:&nbsp; aws:region, aws:account:id, boolean, integer, float, binary, hostname, email, ipv4-address, and ipv6-address. You can combine a data type with an AllowedPattern for additional constraints, and you can change the data type of an existing text parameter.</p>

You can set this up using the AWS Management Console, AWS CLI, or AWS SDK. You can use self-managed AD without any additional charge.</p> 
<p>Kerberos authentication with self-managed Active Directory in Amazon RDS for Oracle is available in <a href="https://aws.amazon.com/about-aws/global-infrastructure/regional-product-services/">all commercial AWS Regions</a> where Amazon RDS for Oracle is available. To learn more about Kerberos authentication with self-managed Active Directory, visit <a href="https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/oracle-smad.html" rel="noopener noreferrer" target="_blank">Working with self-managed Active Directory with an Amazon RDS for Oracle DB instance</a> in the Amazon RDS User Guide.</p>
