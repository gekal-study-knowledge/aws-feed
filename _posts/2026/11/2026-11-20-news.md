### Amazon Aurora DSQL now supports multi-Region peering across continents

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/aurora-dsql-intercontinental-multi-region-clusters/](https://aws.amazon.com/about-aws/whats-new/2026/11/aurora-dsql-intercontinental-multi-region-clusters/)
- **Published**: 2026-11-20 00:56:00
- **Fetched**: 2026-11-20 03:48:46

<div class="entry-summary">
<p><a href="https://aws.amazon.com/rds/aurora/dsql/">Amazon Aurora DSQL</a> now lets you create multi-Region clusters whose Regions are on different continents, such as US East (N. Virginia) and Europe (Ireland). Until now, the Regions in a multi-Region cluster had to be in the same geographic Region set.</p> 
<p>With intercontinental multi-Region clusters, applications on two continents read and write to one strongly consistent database. If a Region becomes unavailable, committed writes are preserved and applications keep reading and writing in the other Region. You choose the two peer Regions and the witness Region. Place your database close to users on each continent, or separate failure domains as widely as your resilience needs require.</p> 
<p>Intercontinental multi-Region clusters are available in all <a href="https://aws.amazon.com/about-aws/global-infrastructure/regional-product-services/">AWS Regions</a> where Aurora DSQL supports multi-Region clusters. To learn more, see <a href="https://docs.aws.amazon.com/aurora-dsql/latest/userguide/what-is-aurora-dsql.html#aurora-dsql-multi-region-availability">Multi-Region cluster availability</a> in the Aurora DSQL User Guide.</p>
</div>

### Amazon Aurora now supports moving clusters to a different VPC

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/aurora-move-clusters-to-different-vpc/](https://aws.amazon.com/about-aws/whats-new/2026/11/aurora-move-clusters-to-different-vpc/)
- **Published**: 2026-11-20 02:00:00
- **Fetched**: 2026-11-20 10:00:05

<div class="entry-summary">
<p>Aurora PostgreSQL and Aurora MySQL clusters can now move from one Amazon Virtual Private Cloud (VPC) to another without data migration. You can move a cluster with a single API call or a modify action in the Amazon RDS console. This lets you move a cluster to a VPC with more IP address space or a non-overlapping CIDR range, consolidate your network architecture, or meet changing security and compliance requirements.</p> 
<p>Previously, moving an Aurora cluster to a different VPC meant creating a new cluster in the target VPC, migrating your data, and updating your applications with new connection strings. Now, a single ModifyDBCluster API call moves your existing cluster to the new VPC. Your data stays in place, your cluster endpoint stays the same, and connectivity is interrupted only briefly during the move. Before you start, turn off features that are tied to the cluster's current VPC, such as Aurora Global Database, Amazon RDS Proxy, and Amazon RDS Blue/Green Deployments. You can set them up again in the new VPC after the move.</p> 
<p>This feature is available for Aurora PostgreSQL and Aurora MySQL in all <a href="https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/CHAP_GettingStartedAurora.AuroraPostgreSQL.ExpressConfig.html#CHAP_GettingStartedAurora.AuroraPostgreSQL.ExpressConfig.SupportedRegions" target="_blank">AWS Regions</a> where Aurora PostgreSQL with express configuration is available. To get started, use the <a href="https://console.aws.amazon.com/rds/home" rel="noopener noreferrer" target="_blank">Amazon RDS console</a>, AWS CLI, or AWS SDKs. To learn more, see the <a href="https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/USER_VPC.WorkingWithRDSInstanceinaVPC.html#USER_VPC.WorkingWithRDSInstanceinaVPC.UpdatingVPC" rel="noopener noreferrer" target="_blank">Aurora User Guide</a>.</p>

### AWS Elemental MediaTailor adds Dynamic Avail Sizing for live HLS

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/aws-elemental-mediatailor-dynamic-avail-sizing-live-hls](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-elemental-mediatailor-dynamic-avail-sizing-live-hls)
- **Published**: 2026-11-20 03:00:00
- **Fetched**: 2026-11-20 10:00:05

<div class="entry-summary">
<p>AWS Elemental MediaTailor now supports Dynamic Avail Sizing, which reduces the slate viewers see when ad breaks, also called avails, in live HLS streams go unfilled. MediaTailor is a server-side ad insertion and channel assembly service that personalizes ads in live and on-demand video streams.</p> 
<p>When the ad decision server returns fewer ads than a break allows, dynamic avail sizing omits the unfilled time and resumes programming early instead of showing slate. To keep playback continuous, MediaTailor holds back a configurable reserve of content behind the live edge and draws on it when a break ends early. When the reserve runs low, MediaTailor requests extra ad time in later breaks to refill it. Free ad-supported streaming TV (FAST) channel operators can use dynamic avail sizing to keep viewers watching programming instead of filler content.</p> 
<p>Customers turn on dynamic avail sizing for each playback session by adding query parameters to the session initialization URL, with no change to their playback configuration. To learn more, see <a href="https://docs.aws.amazon.com/mediatailor/latest/ug/dynamic-avail-sizing.html">Dynamic avail sizing</a> in the AWS Elemental MediaTailor User Guide.</p>
</div>

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/02/aws-waf-security-analytics-dashboard/](https://aws.amazon.com/about-aws/whats-new/2026/02/aws-waf-security-analytics-dashboard/)

- **Fetched**: 2026-11-20 10:00:05

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>AWS WAF now gives you one place to find and stop unwanted traffic across every application in your account. The new AWS WAF security analytics dashboard brings together traffic from all of your protection packs (web ACLs), whether they protect Regional resources or Amazon CloudFront distributions, into a single view. The dashboard also lets you search request logs right in the console, with no logging pipeline to build, and includes 21 days of full-fidelity request data at no additional cost. It is available alongside the existing dashboard for each protection pack (WebACL), which continues to work as it does today.</p> 
<p>Until now, spotting a trend across your applications, such as a bot campaign hitting several endpoints or a spike in blocked requests, meant opening each web ACL in turn or individually querying AWS WAF logs. With the AWS WAF security analytics dashboard, you can analyze traffic data from every protection pack (WebACL) at once. You can filter and group traffic by dimensions such as client IP address, country, ASN, user agent, JA4 fingerprint, host, path, rule triggered, and labels. You can see which endpoints are affected and how traffic is changing across all of them. The data is full-fidelity rather than sampled, and filters apply across the whole dashboard.</p> 
<p>Investigating individual requests has also required delivering AWS WAF logs to Amazon CloudWatch Logs, Amazon S3, or Amazon Data Firehose and writing queries. AWS WAF Security analytics dashboard includes a logs widget that lets you search and explore raw request logs in the console, down to the full HTTP request, with no log delivery to configure. When you find unwanted traffic, you can block an IP address or a country directly from the page. You can also filter by the labels that managed rules attach to requests to see what a rule in Count mode would block before you enforce it.</p> 
<p>The AWS WAF security analytics dashboard is available at no additional cost in all commercial AWS Regions where AWS WAF is available. This feature is not available in the AWS GovCloud (US) Regions and China Regions. To get started, open the AWS WAF console and choose Security analytics in the navigation pane.&nbsp;To learn more, see the <a href="https://docs.aws.amazon.com/waf/latest/developerguide/web-acl-security-analytics.html" rel="noopener noreferrer" target="_blank">AWS WAF Developer Guide</a>&nbsp;and <a href="https://aws.amazon.com/blogs/security/introducing-the-new-aws-waf-security-analytics-dashboard/" rel="noopener noreferrer" target="_blank">launch blog post</a>.</p>

<p>AWS Lambda now supports a 30-minute function timeout for <a href="https://docs.aws.amazon.com/lambda/latest/dg/lambda-functions-chapter.html">Event Functions</a> that run on demand, doubling the 15-minute limit for <a href="https://docs.aws.amazon.com/lambda/latest/dg/invocation-sync.html">synchronous</a>, <a href="https://docs.aws.amazon.com/lambda/latest/dg/invocation-async.html">asynchronous</a>, and <a href="https://docs.aws.amazon.com/lambda/latest/dg/invocation-eventsourcemapping.html">event source mapping (ESM)</a> invocations. On <a href="https://docs.aws.amazon.com/lambda/latest/dg/lambda-managed-instances.html">Lambda Managed Instances</a>, synchronous invocations also support up to 30 minutes, while asynchronous and ESM invocations keep the <a href="https://aws.amazon.com/blogs/compute/announcing-90-minute-function-timeout-on-aws-lambda-managed-instances/">90-minute timeout</a> launched in September 2026. You can now run long-running workloads such as AI inference, media transcoding, and financial calculations for spiky or steady-state traffic without re-architecting your applications.</p> 
<p>Customers use&nbsp;Event Functions to build event-driven processors, API backends, and data pipelines. By default, Event Functions run on demand, and Lambda scales them automatically to handle spiky traffic. For steady-state traffic, you can also run them on Lambda Managed Instances, which runs functions on Amazon EC2 instances and&nbsp;maintains&nbsp;the operational simplicity of Lambda.&nbsp;For data-intensive workloads such as AI inference and media processing that run on demand and need longer continuous execution, the 15-minute function timeout had required customers to adopt&nbsp;architectural workarounds. With today's launch, these workloads can run for up to 30 minutes, including when you use <a href="https://docs.aws.amazon.com/lambda/latest/dg/durable-functions.html">Lambda durable functions</a> or invoke your functions from <a href="https://docs.aws.amazon.com/step-functions/latest/dg/choosing-workflow-type.html">AWS Step Functions Standard workflows</a>.</p> 
<p>For Event Functions that run on demand, the 30-minute timeout is available in all&nbsp;commercial <a href="https://builder.aws.com/build/capabilities">AWS Regions</a>. On Lambda Managed Instances, it is available for synchronous invocations in all Regions where Lambda Managed Instances is available. You can set the function timeout by using the Lambda console, AWS CLI, AWS SDKs, AWS CloudFormation, AWS CDK, or AWS SAM. You can also use coding assistants such as Kiro, Claude Code, or Codex with the <a href="https://docs.aws.amazon.com/lambda/latest/dg/agent-setup-guide.html">Agent Toolkit for AWS</a>. Standard <a href="https://aws.amazon.com/lambda/pricing/">AWS Lambda pricing</a> applies. To learn more, visit the <a href="https://docs.aws.amazon.com/lambda/latest/dg/configuration-timeout.html">AWS Lambda Developer Guide</a>.&nbsp;&nbsp;&nbsp;&nbsp;</p>

<div class="entry-summary">
<p>Amazon Route 53 private hosted zones now support public DNS fallback. When a query for a name in your private hosted zone's domain doesn't match a record in the zone, Route 53 returns the answer from public DNS instead of a "name not found" (NXDOMAIN) error. Public DNS fallback is part of the <a href="https://aws.amazon.com/about-aws/whats-new/2026/11/route-53-offers-advanced-hosted-zones/">Advanced Hosted Zones</a> offering.</p>
<p>Until now, Route 53 treated an associated private hosted zone as fully authoritative for its domain, so queries for names that weren't in the zone returned NXDOMAIN. To resolve a few names privately, customers also had to copy every other record from their public zone into the private hosted zone and keep the two in sync. With public DNS fallback, you add only the names you need privately, and every other name resolves from your existing public DNS. For example, your private hosted zone for example.com points example.com to a private endpoint, while partner.example.com exists only in public DNS. Before, a lookup for partner.example.com returned NXDOMAIN. Now it resolves from public DNS.</p>
<p>To get started, create a private Advanced Hosted Zone or upgrade an existing private hosted zone, and then turn on public DNS fallback. You can use the Route 53 console, API, AWS CLI, AWS SDKs, or AWS CloudFormation.</p>

<p>A single mistaken DNS change can take part of your domain offline, such as deleting a record that is still serving traffic or removing a delegation that resolvers are still using. - **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/11/route-53-affinity-routing/](https://aws.amazon.com/about-aws/whats-new/2026/11/route-53-affinity-routing/)
- **Published**: 2026-11-20 17:21:00
- **Fetched**: 2026-11-21 14:27:21

<div class="entry-summary">
<p>Amazon Route 53 now supports Availability Zone (AZ) affinity routing, which routes DNS queries from your VPCs to resources in the same AZ as the client that sends the query. This helps you keep traffic within the same AZ as the client, reducing latency and improving application performance.</p> 
<p>Until now, customers who wanted lower latency used other routing policies, such as latency-based or geoproximity routing. With this launch, DNS queries from your clients are answered with resources in the same AZ. This keeps traffic within the AZ and gives your clients faster responses. If there's no record for the client's AZ, Route 53 falls back to a record for a less specific location: the Zone Group, then the AWS Region, and then Global, in the same order.</p> 
<p>To get started, create AZ-affinity records and choose a location type for each: Availability Zone, Zone Group, Region, or Global. For Availability Zone records, specify the AZ ID, such as use1-az1. You can associate a health check with any AZ-affinity record, whether it's for an AZ, a Zone Group, or a Region. If the endpoint is unhealthy, Route 53 answers with the record for the next location. You can use AZ-affinity routing for records in both public and private hosted zones. The Global record answers queries that don't come from your VPCs, such as queries from the internet. You can create AZ-affinity records with the Route 53 console, API, AWS CLI, AWS SDKs, and AWS CloudFormation.</p> 
<p>AZ-affinity routing is available in all AWS commercial Regions where Route 53 public and private hosted zones are available. To learn more, see the <a href="https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-azaffinity.html">AZ-affinity routing</a> topic in the Route 53 Developer Guide.
