### AWS HealthOmics introduces resource fallback order for Nextflow workflows

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/10/aws-healthomics-resource-fallback-for-Nextflow/](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-healthomics-resource-fallback-for-Nextflow/)
- **Published**: 2026-10-15 01:00:00
- **Fetched**: 2026-10-15 05:24:28

<div class="entry-summary">
<p>Today, AWS HealthOmics introduces the resource fallback directive for tasks in your Nextflow workflows, enabling you to define an ordered list of preferred accelerator types, including an option to fallback to CPU instances. Researchers and bioinformaticians can use this directive to reduce time spent diagnosing and resubmitting runs due to accelerator constraints and keep production workflows running. <a href="https://aws.amazon.com/healthomics/">AWS HealthOmics</a> is a HIPAA-eligible service that helps healthcare and life sciences customers accelerate scientific breakthroughs at scale with fully managed bioinformatics workflows. </p>
<p>With resource fallback for Nextflow workflows, you can prioritize your preferred accelerator for your task. When your preferred accelerator is unavailable, HealthOmics automatically moves through your specified alternatives in the fallback without resubmission. Each accelerator profile has a configurable timeout, giving you control over how long HealthOmics searches for that accelerator before moving to the next. Shorter timeouts help you move quickly through the fallback order, while longer timeouts increase the probability of reserving your preferred accelerator. You can also include a CPU profile as a final fallback to increase the likelihood of your task reserving an instance. </p>
<p>You can now use resource fallback for Nextflow workflows in all AWS HealthOmics Regions: US East (N. Virginia, Ohio), US West (Oregon), Europe (Frankfurt, Ireland, London), Israel (Tel Aviv), and Asia Pacific (Seoul, Singapore, Tokyo). To learn more, visit the <a href="https://docs.aws.amazon.com/omics/latest/dev/advanced-resource-configuration.html">advanced resource configuration</a>&nbsp;and <a href="https://docs.aws.amazon.com/omics/latest/dev/workflow-definition-nextflow.html#workflow-nextflow-directive-fallback">Nextflow specifics</a> documentation. </p>
</div>

- **Fetched**: 2026-10-15 05:24:28

<details class="entry-summary">

<p>Amazon SageMaker Studio now lets new customers sign up with their Google, GitHub, or Apple credentials and land inside a fully configured Studio environment - no traditional AWS account setup, no credit card, and no console navigation required.</p>
<p>Previously, new customers who discovered a model on Hugging Face or an AWS product page had to complete a multi-step AWS account creation process, provide a credit card, navigate the AWS Console to find SageMaker AI, configure an environment, and set up IAM permissions before they could begin working. ### ARC Region switch adds four new capabilities

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/10/region-switch-target-health-ssm-lambda/](https://aws.amazon.com/about-aws/whats-new/2026/10/region-switch-target-health-ssm-lambda/)
- **Published**: 2026-10-15 02:38:00
- **Fetched**: 2026-10-15 08:37:36

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>Amazon Application Recovery Controller (ARC) Region switch helps you orchestrate the failover of multi-Region applications to achieve a bounded recovery time during a Regional impairment. Today, Region switch adds four new capabilities: AWS Systems Manager Run Command execution block, payloads for custom action Lambda execution block, service quota parity checks, and wait for target group health feature for compute scaling actions.</p>
<p><b>AWS Systems Manager Run Command execution block.</b> During failover, you often need to run commands on managed instances and VMs. This execution block lets you invoke Run Command actions on managed instances during failover, with plan evaluation verifying that command documents target valid instances and that IAM permissions are correctly configured.</p>
<p><b>Payloads for custom action Lambda execution block.</b> ARC Region switch now lets you pass payloads to your custom action Lambda execution block, allowing reusability of your Lambda functions across recovery plans.</p>
<p><b>Service quota checks.</b> Service quota limits are a common failure mode during recovery. Region switch now verifies quota parity between your primary and standby Region, and automatically submits quota limit increases, reducing the risk of insufficient service quotas during recovery.</p>
<p><b>Wait for target group health.</b> Amazon ECS service scaling and Amazon EC2 Auto Scaling group execution blocks help you provision compute capacity during recovery, but provisioned capacity may not be ready to serve traffic. The optional wait for target group health feature verifies that your provisioned capacity is ready to serve traffic.</p>
<p>To get started, see the documentation for <a href="https://docs.aws.amazon.com/r53recovery/latest/dg/ssm-send-command-block.html">AWS Systems Manager Run Command execution block&nbsp;</a>,&nbsp;<a href="https://docs.aws.amazon.com/r53recovery/latest/dg/custom-action-lambda-block.html">custom action Lambda execution block&nbsp;</a>, <a href="https://docs.aws.amazon.com/r53recovery/latest/dg/working-with-rs-service-quota-checks.html">Service quota checks&nbsp;</a> and the Wait for target group health for <a href="https://docs.aws.amazon.com/r53recovery/latest/dg/ecs-service-scaling-block.html">Amazon ECS service scaling execution block&nbsp;</a> and <a href="https://docs.aws.amazon.com/r53recovery/latest/dg/ec2-auto-scaling-block.html">Amazon EC2 Auto Scaling group execution block&nbsp;</a>.&nbsp;&nbsp;</p>
</details>

### Amazon CloudWatch announces log routing and chained log parsers

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/10/cloudwatch-pipelines-log-routing/](https://aws.amazon.com/about-aws/whats-new/2026/10/cloudwatch-pipelines-log-routing/)
- **Published**: 2026-10-15 07:14:00
- **Fetched**: 2026-10-15 11:59:42

<div class="entry-summary">
<p>Amazon CloudWatch now supports conditional log routing and chained parsers via pipelines, giving you more control over how log data is transformed and which CloudWatch log group it's sent to. CloudWatch pipelines is a fully managed service that ingests, transforms, and routes telemetry to CloudWatch without managing infrastructure.</p>
<p>Log pipelines often carry a mix of event types that belong in different places, and individual events can nest one log format inside another. With conditional log routing, you define routes that send each event to a different CloudWatch log group based on conditions evaluated against processed fields, so you can separate events by severity, source, or type and apply the right retention and access controls to each. With chained parsers, you can apply multiple parser processors in sequence, where later parsers consume fields produced by earlier ones. For example, you can parse a JSON envelope first, then apply a Grok parser to a field it extracts. Together, these capabilities let you structure diverse log formats and route them to the right log groups in a single pipeline.</p>
<p>Conditional routing and chained parsers are available in all commercial AWS Regions where CloudWatch pipelines is generally available. You can configure these capabilities using the AWS Management Console, AWS CLI, or AWS SDKs. To get started, see the <a href="https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/cloudwatch-pipelines.html">Amazon CloudWatch pipelines documentation</a>.</p>
</div>

 <b>Publication Date:</b> 10/14/2026 12:30 PM PDT</p>

<p>We identified CVE-2026-110310, an issue in Amazon S3 encryption client for .NET that could allow a remote user who can read encrypted objects in the S3 bucket can force a padding downgrade by altering the padding scheme recorded in an object's metadata to legacy PKCS#1 v1.5.
