### AWS announces TorchNeuron: Native PyTorch Support for AWS Trainium (Public Beta)

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/10/aws-announce-native-pytorch-support-trainium](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-announce-native-pytorch-support-trainium)
- **Published**: 2026-10-21 00:00:00
- **Fetched**: 2026-10-21 03:17:01

<div class="entry-summary">
<p>Today, AWS launched the public beta of TorchNeuron, an open source native PyTorch backend for AWS Trainium. Trainium is a portfolio of AI chips designed to deliver high performance and cost efficiency for deep learning AI training and inference workloads. TorchNeuron enables AI scientists and researchers to experiment and build models with PyTorch natively on Trainium.</p>

### Amazon WorkSpaces simplifies secure AI agent access to enterprise cloud desktops with less infrastructure to operate and manage

- **Fetched**: 2026-10-22 02:52:11

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>WorkSpaces for AI agents now handles authentication and desktop connections as part of the managed Model Context Protocol (MCP) service, so you can connect agents to governed cloud desktops, removing the need to write custom code. This makes it easy to use WorkSpaces with any client that supports MCP.</p> 
<p>Connecting an agent to a desktop previously required you to manage presession requirements; generate, invoke, and rotate streaming URLs manually, adding complexity every time a session expired. You can now create sessions with your existing AWS credentials through OAuth 2.0, and the service handles the connection lifecycle. You configure once which desktop stack to use, and your agents reach the right desktop without ever seeing or handling the underlying streaming connection. <p>WorkSpaces for AI agents runs agent sessions inside the same network isolation and compliance boundaries that govern your human workforce, inheriting the VPC controls, data-loss prevention policies, and session-level security posture that enterprises have already configured. The service is also now available in four additional AWS Regions: South America (São Paulo), Europe (Milan), Europe (Spain), and Asia Pacific (Malaysia).</p>

### Amazon DynamoDB global tables now support disassociating replicas

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/10/dynamodb-global-tables-disassociate/](https://aws.amazon.com/about-aws/whats-new/2026/10/dynamodb-global-tables-disassociate/)
- **Published**: 2026-10-21 08:00:00
- **Fetched**: 2026-10-21 10:13:43

<div class="entry-summary">
<p><a href="https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Introduction.html">Amazon DynamoDB</a> global tables now support disassociating a replica without deleting its table or data. Global tables provide fully managed, multi-Region, multi-active replication. You can now stop replication to and from a replica and continue using the same table as a single-Region table.</p> 
<p>An account can leave a shared multi-account global table and continue using its table independently. You can also stop replication to a Region while keeping its table for local workloads, validation, or audit, without creating a replacement table or copying data.</p> 
<p>DynamoDB supports disassociating replicas in all AWS Regions for same-account and multi-account global tables that use multi-Region eventual consistency (MREC).</p> 
<p>To get started, use the AWS Management Console, AWS CLI, DynamoDB API, or AWS CloudFormation. For more information, see <a href="https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/globaltables-disassociate.html">Disassociating replicas</a> in the Amazon DynamoDB&nbsp;Developer Guide.</p>

### Announcing Amazon ECS Gateway, a managed ingress solution for your ECS services

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/10/announcing-amazon-ecs-gateway/](https://aws.amazon.com/about-aws/whats-new/2026/10/announcing-amazon-ecs-gateway/)
- **Published**: 2026-10-21 08:26:00
- **Fetched**: 2026-10-21 10:13:43

<details class="entry-summary">
<summary>詳細を表示</summary>
<p>AWS announces Amazon Elastic Container Service (Amazon ECS) Gateway, a new resource that simplifies ingress networking for containerized applications by dynamically provisioning and managing Application Load Balancers (ALBs) and their supporting resources directly in your account.</p> 
<p>With ECS Gateway, platform teams define organizational networking standards once on a gateway and associate it with one or more clusters, giving organizations a centralized way to govern how traffic reaches their ECS services. Application teams simply opt in to inherit those standards without requiring networking expertise. ECS Gateway offers host-based routing, allows up to 25 services to share an ALB to optimize infrastructure costs, and gives each service a unique Domain Name System (DNS) hostname. ECS manages the full lifecycle of the underlying infrastructure, provisioning the first ALB when your first service connects, adding more ALBs when capacity is reached, and removing them when no longer needed. You can inspect these resources and the gateway route to each service to see exactly how requests reach your applications. For traffic and health monitoring, you can use standard ALB metrics in Amazon CloudWatch and target health information from Elastic Load Balancing.</p> 
<p>To get started, create an ECS Gateway, associate it with a cluster, and opt in your ECS service by adding the gateway connector parameter using the AWS Management Console, AWS CLI, API, AWS SDKs, or AWS CloudFormation. ECS Gateway is available for ECS services using the awsvpc network mode across all launch types. It is available now in all commercial AWS Regions at no additional charge. You pay only for the underlying infrastructure provisioned in your account when your services connect to the gateway. To learn more, refer to the <a href="https://aws.amazon.com/blogs/aws/introducing-amazon-ecs-gateway-a-fully-managed-ingress-solution-for-ecs-services">AWS News blog</a> and our <a href="https://docs.aws.amazon.com/AmazonECS/latest/developerguide/gateway-overview.html">documentation</a> page.</p>
</details>

### CVE-2026-112380 - Missing authorization in the WhatsApp channel in Kiro Crew

- **Link**: [https://aws.amazon.com/security/security-bulletins/rss/2026-140-aws/](https://aws.amazon.com/security/security-bulletins/rss/2026-140-aws/)
- **Published**: 2026-10-21 05:19:42
- **Fetched**: 2026-10-21 07:02:38

<div class="entry-summary">
<p><b>Bulletin ID:</b> 2026-140-AWS
 <br />
 <b>Scope:</b> AWS
 <br />
 <b>Content Type:</b> Important (requires attention)
 <br />
 <b>Publication Date:</b> 10/20/2026 13:00 PM PDT</p>
<p><b>Description:</b></p>
<p>Kiro Crew is an open-source personal AI agent that can be reached from a web dashboard, a CLI, or messaging channels such as WhatsApp, and that runs tools on the operator's machine.</p>
<p>We identified CVE-2026-112380, an authorization issue in the WhatsApp channel and the internal subagent run-control endpoints. In certain configurations where a WhatsApp group was added to an operator's allowed groups, or where the direct-message policy was set to open, a member of that WhatsApp group could send instructions to another session's subagent. The subagent then executed those instructions on the operator's machine under that session's approval policy, and the resulting audit trail was attributed to the operator rather than the actual sender.</p>
<p>The default configuration is not affected: whatsapp.groups defaults to empty and whatsapp.dm_policy defaults to self, so a group that is not explicitly listed is dropped before dispatch.</p>
<p><b>Impacted versions:</b> &gt;=0.4.0 AND &lt;0.7.2</p>
