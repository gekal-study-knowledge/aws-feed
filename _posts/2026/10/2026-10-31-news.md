### Amazon Connect Customer now supports versioning and aliasing for flows

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/10/connect-flows-versioning-aliasing/](https://aws.amazon.com/about-aws/whats-new/2026/10/connect-flows-versioning-aliasing/)
- **Published**: 2026-10-31 00:00:00
- **Fetched**: 2026-10-31 10:24:08

<div class="entry-summary">
<p>Amazon Connect Customer now supports versioning and aliasing for flows and flow modules, simplifying how you build, test, and deploy customer experience flows while minimizing impact to live end-customer traffic. With this launch, you can now create immutable versions of a flow and attach one or more friendly names (i.e., aliases) to a version, then point resources such as queues, quick connects, and phone numbers at an alias instead of a specific version.</p> 
<p>Rolling out a new version takes a single update, with no need to republish or relink each resource. For example, you can publish an updated customer experience flow as a new version and validate it in a test environment while live traffic stays on the current version, then repoint the production alias to move every phone number to the new version in a single update.</p> 
<p>This feature is available in all AWS Regions where Amazon Connect Customer is offered. To learn more, see <a href="https://docs.aws.amazon.com/connect/latest/adminguide/flows-versions-aliases.html">Flow versioning and aliasing</a> in the Amazon Connect Customer Administrator Guide. To learn more about Amazon Connect Customer, an agentic AI solution that helps enterprises deliver exceptional customer experiences, visit the <a href="https://aws.amazon.com/products/connect/customer/">Amazon Connect Customer website.</a></p>
</div>

### AWS WAF announces automatic SDK integration for Amazon CloudFront distributions

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/10/aws-waf-automatic-sdk-integration-amazon-cloudfront/](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-waf-automatic-sdk-integration-amazon-cloudfront/)
- **Published**: 2026-10-31 00:57:00
- **Fetched**: 2026-10-31 06:21:30

<div class="entry-summary">
<p>AWS WAF announces automatic SDK integration for Amazon CloudFront distributions. When you enable it, CloudFront adds the script tag for the AWS WAF JavaScript SDK to the HTML it serves, with no change to your application code, build process, or deployment. The SDK supplies the client-side signals used by three AWS WAF managed rule groups: Bot Control at the targeted inspection level, Fraud Control account takeover prevention (ATP), and Fraud Control account creation fraud prevention (ACFP).<br /> <br /> Previously, supplying those signals required you to add a script tag to every page of every application you wanted to protect, and to maintain that tag across releases. For teams running many applications, or serving pages produced by systems they do not control, this created recurring work and a common source of misconfiguration, where a protection was enabled in AWS WAF but the client-side integration was missing. Enabling automatic SDK integration on the web ACL protecting your CloudFront distribution removes that per-application work.<br /> <br /> Automatic SDK integration is available for web ACLs that are used with Amazon CloudFront and contain at least one of those managed rule groups. You can configure it using the AWS Management Console, CLI, SDK, CDK, or CloudFormation. In the AWS WAF console, the setting appears with the managed rule group settings and is on by default for new web ACLs that you create with one of those rule group. When you create a web ACL programmatically, the setting is off by default. Web ACLs created before this release are unchanged.<br /> <br /> There is no additional charge for automatic SDK integration. For requirements, limitations, and Content Security Policy guidance, see <a href="https://docs.aws.amazon.com/waf/latest/developerguide/waf-challenge-javascript-sdk-injection.html">Automatic SDK integration for CloudFront distributions</a> in the AWS WAF Developer Guide.</p>
</div>

### Amazon MSK now supports TLS 1.3 for data in transit

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-msk-tls/](https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-msk-tls/)
- **Published**: 2026-10-31 02:00:00
- **Fetched**: 2026-10-31 06:21:30

<div class="entry-summary">
<p>Amazon MSK now supports version 1.3 of Transport Layer Security (TLS) protocol for MSK Provisioned clusters through encryption policies. TLS 1.3 delivers faster, more secure encryption for streaming data and is increasingly required by compliance frameworks and enterprise security standards. It is also one of the prerequisites for post-quantum cryptography for protecting data against attacks that collect encrypted traffic now with the intent to decrypt it later.</p> 
<p>Customers can opt in to TLS 1.3 by selecting a named security policy in their MSK cluster configuration, with no change to existing clusters until a policy is applied. A named security policy defines which TLS version and cipher suites a cluster can accept. With this launch, Amazon MSK provides a set of policies customers can select and any connection that does not meet the selected policy requirements is rejected. This allows customers to stay in control of their security and compliance posture. Policies that support both TLS 1.2 and TLS 1.3 allow connections to negotiate the highest version the client supports allowing clients that support TLS 1.3 to connect on it immediately while clients on TLS 1.2 continue to connect on TLS 1.2. This lets customers upgrade their clients at their pace before applying a stricter policy. Customers can also select stricter policies that align closer with their compliance requirements to restrict connections to TLS 1.3 only.</p> 
<p>This capability is available at no additional cost in all AWS Regions where Amazon MSK Provisioned is available. To learn more, see the <a href="https://docs.aws.amazon.com/msk/latest/developerguide/security.html">Amazon MSK documentation</a>.</p>
</div>

### Amazon CloudFront now provides viewer ISP and post-quantum TLS details

- **Link**: [https://aws.amazon.com/about-aws/whats-new/2026/10/cloudfront-viewer-isp-post-quantum-visbility/](https://aws.amazon.com/about-aws/whats-new/2026/10/cloudfront-viewer-isp-post-quantum-visbility/)
- **Published**: 2026-10-31 03:15:00
- **Fetched**: 2026-10-31 06:21:30

<div class="entry-summary">
<p>Amazon CloudFront can now forward two new optional headers to your origin. The CloudFront-Viewer-ISP header contains the name of the viewer's internet service provider (ISP), so you can see which network a request came from. The CloudFront-Viewer-TLS-Details header describes the cryptography used on each viewer's TLS connection, so you can see whether a connection used post-quantum cryptography (PQC).</p> 
<p>With CloudFront-Viewer-ISP, you can break down traffic and performance by network. You can also isolate unusual traffic from a single provider. CloudFront-Viewer-TLS-Details includes the key exchange, signature scheme, and signature public key type for each connection. You can use it to measure the share of viewers that actually connect with PQC and identify clients that do not yet do so. To forward either header to your origin, add it to an origin request policy and attach the policy to your distribution.</p> 
<p>To get started, see <a href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/adding-cloudfront-headers.html">adding CloudFront headers</a> and&nbsp;<a href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/controlling-origin-requests.html">controlling origin requests with a policy</a> in the Amazon CloudFront Developer Guide</p>
</div>
